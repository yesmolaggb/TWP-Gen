# Evaluation Method

This document describes how generated technical white papers are scored. It is the
prose companion of `evaluation_method.json`. All generation tasks come from
`whitepaper_topics.json`.

## 1. Overview

Each generated document is assessed along two independent tracks:

| Track | Assessed by | Output |
|---|---|---|
| Automatic scoring | An LLM evaluator of the same series as the generator | Ten 0--5 metric scores |
| Human evaluation | Two graduate student evaluators | One acceptability label per document |

The automatic track measures content quality, white-paper adaptability and evidence
credibility. The human track measures whether the document is practically usable.

## 2. Automatic scoring

### 2.1 Scale

Every metric is scored on a 0--5 integer scale. `0` means the document does not
satisfy the criterion at all; `5` means it fully satisfies the criterion. The ten
metric scores are combined by an unweighted mean into a single overall score; no
metric is given extra weight.

### 2.2 Evaluators and generation backbones

| Role | Model | Notes |
|---|---|---|
| Generation backbone | Qwen3-14B without Reasoning | Documents compared under the smaller backbone |
| Generation backbone | Qwen3-32B with Reasoning | Primary backbone |
| Primary evaluator | Qwen3-32B | Scores all generated documents |
| Robustness evaluator | DeepSeek-V3 | Scores only the documents generated by Qwen3-32B |

DeepSeek-V3 is used as an evaluator-robustness check. It never generates documents,
and its scores are reported separately from the primary evaluation.

### 2.3 Metrics

**Content quality** measures how well the document addresses the input topic.

| Metric | Definition |
|---|---|
| Relevance | Whether the document remains consistently aligned with the input topic and avoids irrelevant or generic digressions. |
| Breadth | Whether it covers the major background, principles, components, applications, challenges, evaluation aspects, and implications expected for the topic. |
| Depth | Whether it explains mechanisms, implementation details, module relationships, trade-offs, limitations, and technical implications beyond surface-level description. |
| Novelty | Whether it provides useful additional perspectives, comparisons, challenges, trends, or future directions beyond directly restating the topic. |

**White-paper adaptability** evaluates compliance with technical white-paper writing
conventions.

| Metric | Definition |
|---|---|
| Technical Specificity | Whether core principles, system architecture, components, workflows, advantages, limitations, and deployment considerations are discussed with professional technical detail. |
| Understandability | Whether the document is clear, coherent, readable, and uses technical terminology accurately and consistently. |
| Structurality | Whether the section hierarchy, content order, section functions, transitions, and overall organization conform to technical-white-paper conventions. |

**Evidence credibility** assesses the reliability and traceability of generated
content.

| Metric | Definition |
|---|---|
| Citation Sufficiency | Whether key technical concepts, mechanisms, data, conclusions, and application claims receive adequate citation support across the document. |
| Citation Validity | Whether citation identifiers can be matched to accessible references and whether each cited source directly supports its associated claim. |
| Factual Consistency | Whether technical concepts, entities, relationships, mechanisms, and numerical statements agree with the retrieved evidence without contradiction or unsupported additions. |

### 2.4 Scoring protocol

For every generation topic, the candidate documents are first anonymized by removing
method names and then randomly reordered. The evaluator does not receive the
reference white paper, so the score cannot be produced by comparing the output to
the original document.

The ten metrics are divided into the three groups above. Each group is evaluated
through a separate model call: the call receives the definitions of its constituent
metrics together with the group-specific 0--5 rubric, and returns one independent
score per metric. No aggregate group score is requested from the evaluator. Each
document is evaluated three times, and the final score of each metric is the
arithmetic mean of the three runs.

The evaluator runs with reasoning enabled and a temperature of 0.1. Identical
evaluator settings, anonymization, randomized ordering and repeated scoring are
applied to every method, so differences between methods cannot be attributed to
evaluator configuration, method identity or output position.

The evaluator is instructed to return:

```text
[RESULT] Score: <score from 0 to 5>
<detailed feedback>
```

### 2.5 Rubrics

#### Content Quality

| Score | Operational definition |
|---|---|
| 0 | The document is essentially unrelated to the topic, provides almost no meaningful coverage, is extremely superficial, and contains no meaningful additional insight. |
| 1 | The document has only weak relevance, covers one or two narrow aspects, provides shallow descriptions with little explanation, and adds very little new perspective. |
| 2 | The document is partially relevant and covers some major aspects, but substantial gaps remain. Technical explanations are generally undeveloped, and the additional ideas are limited, generic, or weakly connected. |
| 3 | The document is mostly relevant and covers the main aspects at an acceptable level. It provides moderate depth on several key points and introduces some useful additional perspectives, although noticeable omissions remain. |
| 4 | The document remains clearly focused on the topic, covers most important aspects, explains them with clear detail, and provides several relevant insights, examples, or connections. |
| 5 | The document is consistently aligned with the topic, provides comprehensive and well-balanced coverage, offers deep and rigorous explanations, and introduces valuable, well-integrated perspectives beyond the obvious scope. |

#### White-Paper Adaptability

| Score | Operational definition |
|---|---|
| 0 | The document contains almost no concrete technical content, is largely unreadable or incoherent, and lacks an effective organizational structure. |
| 1 | The document mentions only a few technical terms without explaining their principles or mechanisms. It is difficult to understand, and its section hierarchy, order, and functions are unclear. |
| 2 | The document provides some technical detail, but the content is shallow, scattered, or generic. Parts are understandable, while the overall structure remains incomplete or poorly organized. |
| 3 | The document explains several relevant technical principles or components at an acceptable level and has recognizable sections in a mostly reasonable order. However, some mechanisms, transitions, or structural relationships remain underdeveloped. |
| 4 | The document presents clear technical principles, components, workflows, benefits, and some limitations. It is coherent and readable and follows a clear and logical white-paper structure with only minor weaknesses. |
| 5 | The document systematically explains its technical principles, mechanisms, architecture, workflows, benefits, limitations, and implementation issues. It is highly clear and readable and has an excellent white-paper structure with coherent hierarchy and natural transitions. |

#### Evidence Credibility

| Score | Operational definition |
|---|---|
| 0 | The document contains no identifiable citations or evidence support. Its citations are invalid or cannot be matched to the reference materials, and it contains numerous contradictory or unverifiable technical claims. |
| 1 | The document contains very few citations, leaving most key claims unsupported. Most citations are invalid or untraceable, and serious factual inconsistencies or unsupported technical conclusions are present. |
| 2 | The document provides some citations, but their coverage is clearly insufficient. Some citations can be matched, although numbering, evidence alignment, or traceability problems remain, and several technical claims are exaggerated, mismatched, or unverifiable. |
| 3 | Citations generally cover the main content, and most of them can be matched to relevant reference materials. The document is factually credible overall, although some important claims or details remain weakly supported or slightly inconsistent. |
| 4 | Citations adequately cover most key technical claims and major sections. They are generally valid, traceable, and relevant, and most technical concepts, data, mechanisms, and application scenarios are supported by the reference materials. |
| 5 | Citations comprehensively support the key concepts, mechanisms, data, conclusions, and application scenarios. They are clearly matched, complete, highly relevant, and traceable, while the document's technical facts are fully consistent with the reference materials. |

## 3. Human evaluation

To assess practical usability, all 60 generated white papers undergo a human
evaluation. Two graduate students with prior experience in technical white-paper
writing serve as evaluators. System-related identifiers are removed and the
documents are presented in a randomized order. Both evaluators independently review
every document from four aspects: structural completeness, technical clarity,
content coherence and readability, and evidence grounding.

Each document receives one of three labels:

| Label | Meaning |
|---|---|
| Directly Acceptable | The document can be used without substantive revision. |
| Acceptable with Minor Revisions | The document is generally usable but requires localized corrections, supplementary explanations, or minor structural adjustments. |
| Unacceptable | The document has major deficiencies in technical content, organization, readability, or evidence support and requires substantial rewriting. |

When the initial labels differ, the evaluators independently re-examine the document
against the predefined criteria and then discuss the reasons for their judgments
until a consensus label is reached.

## 4. Module-level clustering analysis

The clustering stage needs a setting with observable category labels, because the
retrieved knowledge units of an open-domain generation task have no gold functional
or cluster labels. DuEE is used as a controlled proxy benchmark: it provides
independently labelled Chinese sentence-level instances, and both tasks require
grouping predicate-centred instances into higher-level latent categories.

The clustering module is measured with four quantitative metrics, plus one
qualitative diagnostic:

| Metric | Meaning | Direction |
|---|---|---|
| Adjusted Rand Index (ARI) | Pairwise agreement with the reference partition, corrected for chance | Higher is better |
| Normalized Mutual Information (NMI) | Shared information between predicted clusters and reference types, invariant to cluster identifiers | Higher is better |
| Clustering Accuracy (ACC) | Proportion of mentions matched to reference types after optimal one-to-one assignment | Higher is better |
| B-cubed F1 (B3 F1) | Harmonic mean of item-level cluster precision and recall, reflecting purity and coverage | Higher is better |
| t-SNE projection | Two-dimensional view of cluster compactness and separation | Qualitative only |

All four quantitative metrics are multiplied by 100 when reported. The number of
clusters equals the number of retained event types, and the event-type labels are
withheld from representation learning and from the clustering step itself. Because
t-SNE distorts global distances, the projection is a supporting view rather than
primary evidence; end-to-end white-paper quality is established separately by the
automatic and human evaluations above.
